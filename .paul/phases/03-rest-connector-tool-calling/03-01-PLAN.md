<objective>
## Goal
Let a job (especially a Business Agent job) call an external REST API as a
risky capability, gated exactly like `files`/`terminal`: the model proposes
a request (method/url/headers/body, secrets as `${KEY_NAME}` placeholders it
never resolves itself), a human approves, only then does the real HTTP call
fire — using the `connectors.py` primitives built in Phase 2.

## Purpose
This is the actual revenue-connector capability PROJECT.md's core value
points at: a Business Agent reaching a real external API, not a proposal
that gets logged and never fires. Phase 2 built the safe primitives
(`resolve_secrets`, `redact`, `guard_ssrf`); this phase wires them into the
job lifecycle and adds the one piece Phase 2 explicitly deferred — actually
making the HTTP call, with every redirect hop re-checked.

## Output
- `agent_workforce/connectors.py` (extended: `send_request`)
- `agent_workforce/jobs.py` (extended: `_run_connector_action`, `RISKY_ACTIONS["connector"]`)
- `agent_workforce/db.py` (extended: `SEED_INFRASTRUCTURE` row)
- Tests appended to `agent_workforce/test_server.py`
</objective>

<acceptance_criteria>

## AC-1: send_request performs the HTTP call
```gherkin
Given a URL guard_ssrf allows and a reachable HTTP endpoint
When send_request is called with a method, headers, and body
Then it returns (status_code, response_body_text)
```

## AC-2: Every redirect hop is re-validated
```gherkin
Given a response with a 3xx status and a Location header pointing at a
  private/loopback/link-local/unspecified address
When send_request follows the redirect
Then it raises ValueError before connecting to the redirect target
  (this closes the redirect-chain SSRF gap explicitly deferred from
  Phase 2's SCOPE LIMITS)
```

## AC-3: Redirect chains are bounded
```gherkin
Given a response chain of redirects longer than the configured maximum
When send_request follows them
Then it raises ValueError instead of looping indefinitely
```

## AC-4: Non-HTTP(S) schemes are rejected
```gherkin
Given a URL with a scheme other than http/https
When send_request is called
Then it raises ValueError without attempting any connection
```

## AC-5: Connector capability gates like files/terminal
```gherkin
Given the "connector" infrastructure capability is enabled for an agent
When a job's model output proposes a connector request
Then the job pauses at awaiting_approval, exactly like files/terminal,
  and the real HTTP call only fires after POST /api/jobs/{id}/approve
```

## AC-6: Malformed connector requests fail safely
```gherkin
Given a job's output is not valid JSON, or is missing "url"
When the job is approved
Then approve_job still returns 200, the job completes with a descriptive
  error in its output, and no exception reaches the HTTP layer
  (matches the existing _run_terminal_action pattern: risky actions
  report failure as text, they don't raise into the route handler)
```

## AC-7: Resolved secret values never reach persisted output
```gherkin
Given a connector request whose headers include a ${KEY_NAME} placeholder
When the job is approved (whether the HTTP call succeeds or fails)
Then the job's stored `output` and every job_events label contain no raw
  secret value - only "[REDACTED]" where it appeared
  (binding requirement carried from Phase 2's AUDIT.md: any code path
  reaching jobs.record_event or a persisted jobs.output column MUST call
  redact() first)
```

<!-- audit-added -->
## AC-8: Response body size is bounded
```gherkin
Given an HTTP response whose body exceeds a configured maximum size
When send_request reads it
Then it raises ValueError instead of buffering the entire body into memory
  (this is a single-process local server with no per-request isolation -
  an unbounded read from an external, not-fully-trusted API is a
  memory-exhaustion path that can take the whole app down, not just one
  request)
```

<!-- audit-added -->
## AC-9: Total request time (across redirects) is bounded
```gherkin
Given a chain of requests/redirects whose combined elapsed time exceeds a
  configured ceiling
When send_request is still working through them
Then it raises ValueError instead of continuing
  (per-socket-operation timeouts alone don't bound total elapsed time -
  a slow-but-not-malicious API combined with several redirects could tie
  up the synchronous approve_job request thread well past what
  _run_terminal_action's own MAX_TERMINAL_SECONDS ceiling would ever
  allow for the equivalent risky action)
```

<task type="auto">
  <name>Task 1: HTTP execution with redirect-safe SSRF guarding</name>
  <files>agent_workforce/connectors.py</files>
  <action>
    Add to `agent_workforce/connectors.py` (stdlib only: `http.client`,
    `socket`, `ssl`, `urllib.parse.urljoin` - no new dependency):

    - `MAX_REDIRECTS = 5`, `REQUEST_TIMEOUT = 10` module constants.
    <!-- audit-added -->
    - `MAX_RESPONSE_BYTES = 1_000_000`, `MAX_CONNECTOR_SECONDS = 30`
      module constants (`MAX_CONNECTOR_SECONDS` mirrors the existing
      `_run_terminal_action`/`MAX_TERMINAL_SECONDS` precedent for a risky
      action fired synchronously from `approve_job`).
    - `_connect(ip: str, port: int, hostname: str, use_tls: bool) -> http.client.HTTPConnection`:
      opens a raw socket to `ip`/`port` via `socket.create_connection`, then
      for TLS wraps it with `ssl.create_default_context().wrap_socket(sock,
      server_hostname=hostname)` - `hostname` (not `ip`) is what SNI/cert
      verification checks, so this is what makes it safe to connect to the
      pre-validated IP instead of `hostname` directly. Build the
      `http.client.HTTPConnection`/`HTTPSConnection` with `hostname` as its
      `host` (for the Host header) and assign the pre-connected `sock`
      directly rather than letting `.connect()` re-resolve DNS.
    - `send_request(method: str, url: str, headers: dict[str, str], body: str = "") -> tuple[int, str]`:
      <!-- audit-added -->
      - Record `start = time.monotonic()` before the loop. At the top of
        each iteration, if `time.monotonic() - start > MAX_CONNECTOR_SECONDS`,
        raise `ValueError("connector request exceeded time limit")` (AC-9) -
        per-socket timeouts alone don't bound total elapsed time across a
        redirect chain.
      - Loop up to `MAX_REDIRECTS + 1` times:
        - `urlsplit(url)`; raise `ValueError` if `scheme` not in
          `("http", "https")` (AC-4).
        - Call `guard_ssrf(url)` - this re-runs on every loop iteration, so
          a redirect Location header pointing at a private/internal address
          is caught before connecting (AC-2). Use the first returned
          address to connect via `_connect`.
        - Issue the request (`conn.request(method, path, body=body or
          None, headers=headers)`, `conn.getresponse()`).
          <!-- audit-added -->
          Read the body with a size cap instead of a bare `resp.read()`:
          read in chunks (e.g. `resp.read(65536)`) accumulating into a
          `bytearray`, raising `ValueError("response exceeds MAX_RESPONSE_BYTES")`
          if the accumulated size passes `MAX_RESPONSE_BYTES` before the
          body is exhausted (AC-8) - an unbounded `resp.read()` against a
          single-process local server is a memory-exhaustion path, not
          just a slow response. Decode the accumulated bytes as UTF-8 text
          (`errors="replace"` - a response isn't guaranteed to be valid
          UTF-8), close the connection.
        - If status is a redirect (301/302/303/307/308) and a `Location`
          header is present: resolve it with `urljoin(url, location)` and
          continue the loop (AC-2). Otherwise return `(status, text)`
          (AC-1).
      - If the loop exhausts `MAX_REDIRECTS + 1` iterations without
        returning, raise `ValueError("too many redirects (max N)")` (AC-3).

    Avoid: `requests`/`httpx` or any other new dependency - the existing
    `guard_ssrf`'s returned address list only has value if the caller
    actually connects to it instead of the hostname, which is why this
    can't be done with plain `urllib.request` (its redirect handler
    re-resolves DNS on every hop, silently reopening the exact TOCTOU gap
    Phase 2's audit flagged).
  </action>
  <verify>`uv run python -m unittest agent_workforce.test_server` passes, including new send_request tests in `ConnectorTest`</verify>
  <done>AC-1, AC-2, AC-3, AC-4, AC-8, and AC-9 satisfied</done>
</task>

  <name>Task 2: Wire the connector capability into the risky-action gate</name>
  <files>agent_workforce/jobs.py, agent_workforce/db.py</files>
  <action>

    `("connector", "Connector Desk (call external REST APIs)")` to

    In `agent_workforce/jobs.py`: add `import` of the `connectors` module,
    then:

    - `_run_connector_action(job_id: str, text: str) -> tuple[str, str]`:
      following the exact shape of `_write_file_action`/`_run_terminal_action`
      - takes the job's current output text, returns `(new_text,
      event_label)`, and never raises (AC-6):
      - Parse `text` as JSON. On `json.JSONDecodeError` or a missing/empty
        `"url"` key, return
        `(f"[invalid connector request: {exc}]", "connector request invalid")`
        without going any further.
      - `method = data.get("method", "GET").upper()`,
        `headers = data.get("headers", {})`, `body = data.get("body", "")`.
      - Call `connectors.resolve_secrets(headers, data["url"])`. On
        `ValueError` (placeholder in URL, missing/empty env var), return
        `(f"[connector blocked: {exc}]", f"connector blocked: {exc}")` -
        this path can't leak a secret since resolution never completed.
      - Call `connectors.send_request(method, data["url"], resolved_headers, body)`.
        On `ValueError` (SSRF-blocked target, bad scheme, too many
        redirects) or `OSError` (connection failure), catch it, run
        `connectors.redact(str(exc), secret_values)` on the message
        (defense in depth - an error string should never carry a resolved
        secret either), and return
        `(f"[connector request failed: {redacted_msg}]", "connector request failed")`.
      - On success: `redacted_response = connectors.redact(response_text, secret_values)`.
        Build the label from the hostname only, not the full URL/query
        string: `f"called {method} {urlsplit(data['url']).hostname} -> {status}"`.
        Return `(redacted_response, label)` (AC-1, AC-5, AC-7).
    - Register it: `RISKY_ACTIONS["connector"] = _run_connector_action`.
      `RISKY_CAPABILITIES` derives from `set(RISKY_ACTIONS)` automatically -
      no other change needed. `execute_job`'s existing
      `risky = capabilities & RISKY_CAPABILITIES` gate and
      `apply_risky_actions` dispatch already handle any capability present
      in `RISKY_ACTIONS`, so no changes to `execute_job`, `approve_job`, or
      `reject_job` are needed - this is the same reuse `files`/`terminal`
      already rely on (AC-5).

    Avoid: touching `planner.default_capabilities_for_role_type` - business
    and worker agents already inherit the full globally-enabled capability
    set via a `None` override, so once the Owner enables "connector" via
    the existing infrastructure toggle, any business/worker agent gets it
    the same way it already gets `terminal`/`files`. No planner change
    needed for this to work.
  </action>

<boundaries>

## DO NOT CHANGE
- `agent_workforce/jobs.py`'s `execute_job`, `apply_risky_actions`, or the
  `risky = capabilities & RISKY_CAPABILITIES` gate - the existing generic
  dispatch already handles any capability registered in `RISKY_ACTIONS`;
  adding `"connector"` to that dict is the entire wiring point
- `agent_workforce/routes/agents.py` (`approve_job`, `reject_job`) - no
  route-level change is needed for this capability to work
- `agent_workforce/planner.py` - no change needed; business/worker agents
  already inherit the global capability set via their existing `None`
  override

## SCOPE LIMITS
- No new dependency - `http.client`, `socket`, `ssl`, `urllib.parse` are
  all stdlib
- `connector` ships disabled by default, same as `terminal`/`files` - the
  Owner must explicitly enable it via the existing infrastructure toggle
- Redirects capped at `MAX_REDIRECTS = 5`
- No UI changes - the frontend's existing infrastructure-toggle and
  job-approval surfaces already handle any capability key generically (out
  of scope to verify this plan, but no backend change should require one)
<!-- audit-added -->
- Binary response body fidelity is explicitly deferred: `errors="replace"`
  UTF-8 decoding will corrupt a non-text response body (e.g. an image or
  protobuf payload). Acceptable for this phase since REST/JSON APIs are
  the primary use case and this is a functional limitation, not a security
  gap - revisit if/when a connector target returns binary payloads.

## SECRET HANDLING (binding, carried from Phase 2's AUDIT.md)
- `_run_connector_action` MUST call `connectors.redact()` on every string
  it returns - success response, and every error path - before that text
  reaches `apply_risky_actions`'s return value, which is what lands in
  `jobs.output` and workflow/business-loop continuation text. A secret
  that reaches a workflow's next step would leak into that step's model
  prompt, not just a log - this is a stricter requirement than "don't log
  it," and every return path in Task 2 must honor it.

</boundaries>
